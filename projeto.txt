# ForgeIQ — Manufacturing Intelligence & Data Quality Platform

> End-to-end data platform for manufacturing analytics, machine health, production quality, maintenance intelligence and data quality monitoring.

---

## 📌 Sobre o Projeto

**ForgeIQ** é uma plataforma de dados voltada para análise de operações industriais, combinando dados de máquinas, sensores, produção, qualidade e manutenção.

O projeto será construído utilizando **dados públicos de manufatura**, unificados em um **modelo canônico de uma única fábrica fictícia** (unify-fiction strategy). Datasets de domínio compatível serão mapeados para as mesmas máquinas, linhas e produtos na camada Silver, preservando a proveniência real de cada registro no Bronze.

A plataforma terá como objetivo demonstrar, em um único projeto, conceitos de:

* Data Engineering
* Data Quality
* Data Modeling
* Data Analytics
* Industrial IoT Analytics
* Anomaly Detection
* Data Visualization
* Pipeline Orchestration

O projeto será desenvolvido utilizando **Python como linguagem principal**, com dashboards interativos construídos utilizando **Dash + Plotly**.

---

# 🎯 Problema

Ambientes industriais modernos produzem grandes volumes de dados provenientes de diferentes sistemas e equipamentos.

Sensores, máquinas, linhas de produção, inspeções de qualidade e sistemas de manutenção podem gerar informações em formatos e estruturas diferentes.

Isso cria alguns problemas:

### 1. Fragmentação dos dados

Informações relevantes podem estar distribuídas em diferentes fontes:

```text
Machine Sensors
       │
       ├── Temperature
       ├── Pressure
       ├── Vibration
       └── RPM

Production
       │
       ├── Quantity
       ├── Product
       └── Production Line

Quality
       │
       ├── Defects
       ├── Inspection
       └── Quality Status

Maintenance
       │
       ├── Failures
       ├── Repairs
       └── Downtime
```

Sem uma camada de integração, torna-se difícil analisar a relação entre essas informações.

### 2. Problemas de qualidade dos dados

Dados industriais podem apresentar:

* valores ausentes;
* valores duplicados;
* valores fora de domínio;
* timestamps inválidos;
* sensores com valores impossíveis;
* inconsistências entre tabelas;
* dados atrasados;
* alterações de schema.

Dados incorretos podem gerar análises incorretas e decisões operacionais equivocadas.

### 3. Baixa visibilidade operacional

Mesmo quando os dados existem, pode ser difícil responder perguntas como:

* Qual linha de produção apresenta maior taxa de defeitos?
* Quais máquinas possuem maior downtime?
* Existe relação entre condições dos sensores e defeitos?
* Quais máquinas apresentam comportamento anormal?
* Como a qualidade da produção evolui ao longo do tempo?
* A qualidade dos próprios dados está adequada para análise?

---

# 🎯 Objetivo

O objetivo do **ForgeIQ** é construir uma plataforma de dados capaz de:

1. Integrar datasets públicos de manufatura em um modelo canônico único;
2. Criar pipelines de ingestão e processamento;
3. Implementar uma arquitetura de dados em camadas;
4. Aplicar regras automatizadas de Data Quality;
5. Transformar dados brutos em modelos analíticos;
6. Criar indicadores de produção, qualidade e manutenção;
7. Identificar comportamentos anormais em máquinas;
8. Disponibilizar os resultados através de dashboards interativos em Python;
9. Demonstrar uma arquitetura próxima de um ambiente real de Data Engineering.

# 🏗️ Arquitetura

A arquitetura será baseada em uma abordagem **Medallion Architecture**, com um único engine de processamento (Pandas + dbt/DuckDB) e orquestração leve.

```text
                 PUBLIC DATA SOURCES
            (AI4I, CMAPSS, Quality Inspection)
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
           Sensors   Production   Quality
              │          │          │
              └──────────┼──────────┘
                         │
                         ▼
                    INGESTION
                  Python / Pandas
                         │
                         ▼
                      BRONZE
                Raw / Parquet + metadata
                (fonte, batch_id, ingestion_ts)
                         │
                         ▼
                    DATA QUALITY
                  (Pandera + regras)
                         │
                ┌────────┴────────┐
                │                 │
                ▼                 ▼
          Valid Records       Quarantine
                │
                ▼
                     SILVER
            Clean / Standardized
        + ENTITY RESOLUTION
      (modelo canônico da fábrica:
       mesmas machines, lines, products)
                         │
                         ▼
                   TRANSFORMATION
                 dbt + DuckDB
                         │
                         ▼
                       GOLD
                 Analytical Models
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
          Analytics             Data Quality
              │                     │
              └──────────┬──────────┘
                         ▼
                      DuckDB
                         │
                         ▼
                   Dash + Plotly
```

### Decisões de arquitetura

| Decisão | Escolha | Justificativa |
|---|---|---|
| Processamento | Pandas | Volume cabe em RAM; PySpark só se provará necessário depois |
| Transformação | dbt-core + DuckDB | Um único engine para transformação e consultas |
| Storage | Parquet local | Camada de storage abstraida para migrar a S3/MinIO depois |
| Orquestração | Cron / Prefect leve | Airflow é opcional, só se houver necessidade real |
| Integração de fontes | Modelo canônico único | Entity resolution na Silver; proveniência preservada no Bronze |

# 🧪 Data Quality

A qualidade dos dados será tratada como uma parte central do projeto.

O catálogo de regras será **versionado desde a Phase 1** (arquivo `data_quality/rules/` no repositório, com id, versão, dimensão e severidade por regra).

Dimensões avaliadas:

| Dimensão | Exemplo de regra |
|---|---|
| Completeness | `machine_id IS NOT NULL`, `timestamp IS NOT NULL` |
| Validity | `temperature within range`, `rpm >= 0`, `pressure >= 0`, `production_quantity >= 0` |
| Consistency | `maintenance_end >= maintenance_start`, `production_quantity >= defect_quantity` |
| Uniqueness | chaves compostas (ex: `machine_id + timestamp`) |
| Referential Integrity | `fact_*.machine_id` existe em `dim_machine.machine_id` |
| Freshness | tempo desde a última atualização de cada fonte |

O **DQ Score composto** agrega as dimensões em um índice único (pesos documentados) e é exibido como KPI raiz no dashboard 4.

# 📦 Data Sources

Três datasets públicos, unificados em um **modelo canônico de uma única fábrica fictícia** (unify-fiction strategy).

### Datasets oficiais

| # | Dataset | Papel no ForgeIQ | Origem |
|---|---|---|---|
| 1 | **AI4I 2020 Predictive Maintenance** | Sensores (temp, RPM, torque, tool wear) + falhas (5 modos) | UCI #601 |
| 2 | **NASA CMAPSS FD001** | Frota de unidades (100 engines), séries temporais por cycle, sensores de pressão/temperatura, run-to-failure | NASA Prognostics Data Repository |
| 3 | **MFG-004 Quality Control sample** | Qualidade: units inspected/accepted/rejected, defect type/severity, disposition (scrap/rework), line/shift | Hugging Face (`xpertsystems/mfg004-sample`) |

**Decisão MFG-004 vs Kaggle MLCC:** MFG-004 foi escolhido por download direto sem autenticação e cobrir FPY/scrap/rework/defect type. MLCC é candidato futuro se precisar de `machine_id` na qualidade.

**CMAPSS:** apenas **FD001** na fase inicial (1 condição, 1 fault mode). FD002 fica como extensão opcional.

### Unify-fiction strategy

1. Cada dataset entra no Bronze com proveniência real (`source`, `batch_id`, `ingestion_timestamp`);
2. Na Silver, **entity resolution** mapeia registros para um modelo canônico:
   - `machine_id` canônico (`M0001…`) ← `unit_id` (CMAPSS), `UDI`/`Product ID` (AI4I), `machine`/linha (MFG-004) conforme regra documentada;
   - `event_time` sintético documentado onde a fonte não tem timestamp (ex: AI4I usa ordinal sequencial mapeado para janela de tempo fixa — premissa explícita no data dictionary);
3. Fábrica canônica: 1 linha de qualidade + frota de máquinas única.

O desafio técnico central é **entity resolution & standardization** — não simular que datasets diferentes são a mesma fábrica sem regra.

### Limitações conhecidas (KPIs)

| KPI original | Decisão |
|---|---|
| Production Target | **Removido** — sem fonte |
| OEE | **Removido** do KPI raiz — availability/performance não existem nas fontes |
| Vibration | **Removido** — substituído por Tool wear (AI4I) / sensores CMAPSS |
| MTTR | **Removido** — sem duração de reparo na fonte |
| Preventive × Corrective Maintenance | **Removido** — sem eventos de manutenção classificados |
| Downtime | **Mantido como derivado** — fim de vida/falha + janela de reparo fixa (premissa documentada) |

### Documentação por fonte

Cada fonte será documentada individualmente em `docs/data_sources.md`, incluindo:

* origem;
* licença;
* descrição;
* estrutura;
* periodicidade;
* limitações;
* transformações realizadas.

# 🗄️ Data Layers

## Bronze

Objetivo:

> Preservar os dados originais.

Características:

* formato Parquet;
* mínima transformação;
* metadata de ingestão;
* identificação da fonte;
* batch ID;
* ingestion timestamp.

---

## Silver

Objetivo:

> Criar dados limpos, padronizados e confiáveis no modelo canônico da fábrica.

Processos:

* schema validation;
* tratamento de tipos;
* padronização de timestamps;
* remoção/controlação de duplicidades;
* tratamento de valores inválidos;
* normalização;
* **entity resolution** (mapear registros de diferentes fontes para as mesmas machines/lines/products);
* enriquecimento.

Registros inválidos poderão ser enviados para uma camada de **quarantine**.

---

## Gold

Objetivo:

> Criar modelos preparados para análise.

Tabelas:

```text
dim_machine
dim_product
dim_production_line
dim_date
dim_defect
dim_maintenance

fact_sensor_reading
fact_production
fact_quality
fact_maintenance   -- inclui downtime como métrica/marco desta fato
```

> `downtime` é tratado como parte de `fact_maintenance` (eventos e durações), não como fato separado — evita duplicação de grão.

---

# 📄 Data Contracts

Contratos de dados versionados entre camadas, com schemas validados automaticamente:

| Contrato | De → Para | Conteúdo |
|---|---|---|
| `contract_bronze_silver` | Bronze → Silver | schema esperado, tipos, regras de completeness/validity |
| `contract_silver_gold` | Silver → Gold | chaves estrangeiras, grãos, métricas derivadas |

* Schemas versionados (ex: JSON Schema ou Pandera models com versão).
* Quebra de contrato = falha de pipeline + registro de incidente de DQ.

# 🤖 Anomaly Detection

Após a construção da camada analítica (**Phase 5.5 — antes do dashboard Machine Health**), será implementado o módulo de detecção de anomalias.

Possíveis abordagens:

* Statistical Detection
* Isolation Forest
* Z-Score
* Rolling Statistics

O objetivo não será afirmar que uma máquina necessariamente irá falhar.

O objetivo será identificar:

> **comportamentos que fogem do padrão histórico esperado.**

Exemplo:

```text
Machine M102

Temperature       ↑
Vibration         ↑
RPM               ↑
Pressure          normal

Anomaly Score: 0.91
```

# 🎯 Final Goal

O objetivo final do **ForgeIQ** é demonstrar uma solução completa de **Manufacturing Data Engineering & Analytics**, capaz de transformar dados industriais brutos e heterogêneos em informações confiáveis para análise operacional.

O projeto deverá demonstrar:

```text
Raw Data
   ↓
Data Engineering
   ↓
Data Quality
   ↓
Data Modeling
   ↓
Analytics
   ↓
Visualization
   ↓
Anomaly Detection
```

Mais do que um projeto de Machine Learning ou um dashboard, o **ForgeIQ** será desenvolvido como uma **mini plataforma de dados industrial end-to-end**, com foco em qualidade, rastreabilidade, escalabilidade e análise operacional.
